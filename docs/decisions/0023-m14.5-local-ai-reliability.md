# ADR 0023 — M14.5 Local AI reliability & conversation quality (`avra chat`)

_Status: **Accepted** (owner brief "M14.5", 2026-11-19). Implemented OFFLINE plus
loopback-only evaluation against the already running local Bonsai server. No target, no
Runner, no deployment, no server reconfiguration, no paid API._

## Context — what the owner saw, and the measured causes

| ID | Symptom | Root cause (measured) |
|---|---|---|
| A | HTTP 400 `request (4211/4352/4419 tokens) exceeds the available context size (4096)` | (1) the llama.cpp server ran with **4 parallel slots**, so `-c 16384` gave **4096 tokens per request** (`GET /props`: `total_slots: 4`; the guide's `-np 1` was not in effect). (2) AVRA sent every request unbudgeted: full system prompt (727 tok), all 11 tool schemas (~1130 tok + template overhead), up to 9000 chars of history (~2700 tok in Uzbek), plus tool results; no output reservation, no compaction, no handling of the 400. Baseline reproduction on today's 8192-token slots: item Q2 looped `get_investigation` 7× and failed with `request (10132 tokens) exceeds … (8192)`. |
| B | 3648–4536 input tokens for ordinary messages | "Salom!" with no history = **2112** tokens, 54% of it tool schemas a greeting never uses; history grew with every long (often wrong) earlier reply. |
| C | Unnatural Uzbek ("qo'rsatma", "tug'lanmaydi", "qaramashlik") | Mostly **model capability** (Bonsai 2 27B, 1.58-bit). Contributing software factors: English-only instructions with no Uzbek guidance, the model's own earlier malformed replies replayed verbatim in history, and very long contexts. |
| D | Inconsistent self-knowledge | No authoritative status data: the prompt listed tools only; nothing separated "exists / offered now / offline-tested / live-validated / done this session". |
| E | Live-scan proposal for a read-only request | `request_action` was offered on EVERY turn when a scope was bound; nothing tied the offer to what the owner asked. |
| F | Inconsistent answers to multi-part instructions | The REPL read **one line per model turn**: a pasted 7-line brief became 7 separate model calls ("Tasks:", "1. …"), and pasted terminal output ("YOU ❯", "SYSTEM · …") was sent to the model as instructions. |

## Decision

1. **Context budget** (`avra/chat/context.py`, agent `_fit/_call`). Window = configured
   (`--context-tokens`, `AVRA_LLM_CONTEXT_TOKENS`) → detected (llama.cpp `GET /props`) →
   4096 default for a local model. Output reserve = min(max_tokens, window/3); margin 3%
   (exact count) / 5% (estimate). Prompt size is counted EXACTLY with the server's own
   template + tokenizer (`/apply-template` + `/tokenize`, loopback, no generation); otherwise
   a conservative estimator. The call's `max_tokens` is capped to the reserve, so prompt +
   output always fit. Fitting order: shorten older history → drop old exchanges → shrink
   this turn's tool results. If the owner's own message still does not fit, nothing is sent
   and a clear diagnostic is shown (never silent truncation).
2. **Evidence-preserving compaction** of the MODEL-FACING copy only: protected fields
   (target, port, tool, request/evidence ids, hashes, verdicts, states, approval/action ids)
   are never shortened or re-worded; dropped list items are counted and their
   state/verdict values tallied (4× open + 1× closed stays visible); every compacted
   result is marked with where the full record is (`/details <id>`). Stored evidence,
   audit logs and the conversation file are never modified.
3. **Server context refusal**: parsed into `ContextOverflowError`; the agent rebuilds the
   request smaller and retries **once** (a refused request generated nothing and ran no
   tool). Never retried for live actions (those are not model calls).
4. **Deterministic intent gate** (`avra/chat/intent.py`): GREETING / GENERAL_QUESTION /
   EXPLAIN / SUMMARIZE / COMPARE / READ_ONLY_INVESTIGATION / PLAN / LIVE_ACTION_REQUEST /
   AMBIGUOUS from fixed word lists. It only NARROWS the tools offered: greeting → none;
   capability question → 2 small tools; everything else → read-only tools; `request_action`
   only for an explicit, non-negated action request ("taklif qil", "scan", "propose").
   "No live / skanerlama / only recorded evidence" always wins; "propose … don't run it" is
   a proposal (a proposal never runs); contradictions are AMBIGUOUS. Every tool call is
   re-checked against the exact set offered that turn. `/approve`, the one-shot "ha"
   context and the terminal `[y/N]` are unchanged.
5. **Grounded capabilities** (`avra/chat/capabilities.py`): a dated, hand-maintained
   registry with separate statuses (IMPLEMENTED, OFFLINE_TESTED, LIVE_VALIDATED,
   NOT_TESTED, DISABLED, …) citing their ADR/source, plus runtime facts computed from the
   chat itself (scope bound? execution wired? `/runner` checked THIS run?). A one-line
   digest is in the prompt; `get_capabilities` gives detail. No secrets.
6. **Prompt `chat-v4`**: shorter, same safety invariants, explicit Uzbek guidance
   (standard Latin, small glossary, "use the English term rather than invent a word"),
   "answer every part; if unfinished, ask". Older assistant replies are shortened in the
   model-facing history (owner words and AVRA records are not).
7. **REPL continuity**: lines already waiting in the console (a paste) are joined into ONE
   message (Windows `msvcrt`, POSIX `select`, 50 ms); `"""` starts/ends an explicit block;
   a short message ending in ":" / "," / "va" / "…" is held until the owner continues (an
   empty line sends it as is); AVRA's own echoed UI lines are dropped with a notice.

## Not changed

Policy/scope checks, `ScopeChecker`, audit storage and hash chain, kill switch, Runner,
pipelines, `/approve` semantics, the investigation state machine (M14.1–M14.4). The research
loop keeps its own M9.2 compaction and `count_input_tokens` (unchanged).

## Alternatives considered

- *Only raise `n_ctx`*: hides the problem until the next long chat; does not stop the
  greeting from carrying 1100 tokens of unused schemas, nor `request_action` from being
  offered on read-only requests. Rejected as the only fix (still recommended: `-np 1`).
- *Model-based intent classifier*: costs a model call per message and cannot be trusted for
  a permission-relevant decision. Rejected; deterministic lists, fail-closed.
- *Phrase-replacement "Uzbek fixer"*: would hide, not fix, model errors and could corrupt
  correct text. Rejected.

## Consequences / limits

- Uzbek quality is bounded by the model; see the evaluation in `docs/NEXT_SESSION.md`.
- The intent lists are heuristics: an unusual phrasing of a real action request may be
  classified as read-only (fails closed — the owner rephrases, e.g. "… taklif qil").
- Exact token counting needs llama.cpp's `/apply-template` + `/tokenize`; other servers
  (Ollama) use the conservative estimate.

## Results (2026-11-19)

Offline: `tests/unit/test_m145_chat.py` T01-T19 (40 tests), full suite 2090 passed /
42 skipped / 0 failed. Loopback Bonsai evaluation (`tests/eval/chat_eval`, dataset
`uz-chat-eval-v1`, no scope bound, copy of `data/`): greeting prompt 1942 -> 782 tokens,
largest turn 10329 -> 7998 (xhigh) / 12989 -> 7872 (medium), context overflows 1 -> 0,
deterministic pass 8/18 -> 15/18 (xhigh) and 11/18 -> 15/18 (medium), no live proposal
in any run. Two 600 s generation timeouts occurred on old AND new code (server-side).
Uzbek: fewer of the known malformed forms, but manual review still finds non-standard
words - classified as a model limitation. Full table: `docs/NEXT_SESSION.md`.
